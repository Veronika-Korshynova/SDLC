## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Настоящий Software Design Document (SDD) описывает предполагаемую архитектуру и проектные решения веб-приложения «ПП-План» версии MVP 0.1. Документ предназначен разработчикам, архитектору, тестировщикам и специалистам сопровождения для реализации и проверки требований SRS. Функциональная основа — `SRS.md`; Выбор компонентов, схем API и алгоритмов ниже является **проектным предложением**, если он явно не задан SRS.

### 1.2 Область применения {#12-subject-scope}

Объект проектирования — веб-приложение «ПП-План», релиз MVP 0.1, создающее недельное меню на 7 дней на основании целевого КБЖУ, аллергий, исключённых ингредиентов и пищевых предпочтений. Система показывает рецепты, позволяет заменять блюда, пересчитывает показатели и объединяет ингредиенты в список покупок; личные планы сохраняются. В границы SDD входят браузерный клиент, серверное API, каталог продуктов и рецептов, модуль подбора, проверки ограничений, расчёта нутриентов и хранение данных. 

### 1.3 Определения, акронимы и сокращения {#13-definitions-acronyms-and-abbreviations}

| Term | Definition |
|---|---|
| SRS | Software Requirements Specification — спецификация требований к ПО |
| SysML v2 | Systems Modeling Language v2 — язык моделирования структуры и поведения системы |
| MVP | Minimum Viable Product — минимальная функциональная версия продукта |
| КБЖУ | Калории, белки, жиры, углеводы |
| Каталог рецептов | Проверенный набор рецептов с составом, массой ингредиентов и пищевой ценностью |
| Жёсткое ограничение | Аллерген или явно исключённый ингредиент, который запрещено нарушать при подборе |
| Мягкий критерий | Предпочтение или желательное совпадение с целевым КБЖУ, которое не отменяет запреты |

## 2. Обзор дизайна {#2-design-overview}

### 2.1 Задачи стейкхолдеров {#21-stakeholder-concerns}

| Стейкхолдер | Задача | Представления |
|---|---|---|
| Пользователь | Безопасное меню с учетом аллергий, понятные КБЖУ и покупки | Контекст, интерфейс, алгоритм, взаимодействие |
| Администратор каталога | Поддерживать корректный и актуальный состав рецептов | Информация, логическое, зависимости |
| Разработчики | Разделить ответственность модулей и определить API | Композиция, структура, интерфейс |
| Тестировщики | Проверять безопасность, корректность пересчётов и ошибки | Алгоритм, состояния, взаимодействие |
| Эксплуатация | Обеспечить доступность, восстановление и наблюдаемость | Развёртывание, ресурсы, физическое представление |
| Владелец продукта | Уложиться в рамки MVP и оценить стоимость изменений | Паттерны, зависимости, решения |

### 2.2 Выбранные точки зрения {#22-selected-viewpoints}

Для каждого из следующих пятнадцати ракурсов выбрано словесное представление и, где уместно, модель SysML v2. SysML v2 используется для структуры частей системы (`part def` / `part`) и сценария генерации (`action def`). Схемы в разделе 3 являются проектными представлениями, а не подтверждением существующей реализации.

#### 2.2.1 Контекст {#221-context}

**Выбранное представление:** контекстная модель SysML v2 и границы доверия. Акторы — пользователь и администратор каталога; внешние системы — необязательный поставщик нутриентных данных и платформа хостинга. Адресует REQ-FUNC-001–010, REQ-SEC-001.

#### 2.2.2 Композиция {#222-composition}

**Выбранное представление:** декомпозиция на Web UI, API, User/Profile, Recipe Catalog, Menu Generation, Allergen Validation, Nutrition Calculation, Shopping List и Persistence. Контракты компонентов отделяются от их реализаций. Адресует REQ-FUNC-001–010.

#### 2.2.3 Логическое представление {#223-logical}

**Выбранное представление:** логическая модель типов User, FoodProfile, Restriction, Ingredient, Recipe, RecipeIngredient, WeeklyPlan, PlanDay, MealEntry, ShoppingItem. Связи и ключи описаны в DV-003. Адресует REQ-FUNC-001–010.

#### 2.2.4 Физическое представление {#224-physical}

**Выбранное представление:** браузер пользователя, вычислительный узел веб/API, узел базы данных, резервное хранилище и канал HTTPS. Разделение узлов является вариантом развертывания; отдельные физические серверы для MVP не обязательны. Адресует REQ-SEC-002, REQ-AVAIL-001.

#### 2.2.5 Структура {#225-structure}

**Выбранное представление:** структура системы с вложенными частями `PPPlanSystem`, `WebInterface`, `MenuGenerator`, `AllergenValidator`, `NutritionCalculator`, `ShoppingListBuilder`. Наличие указанных имен в концептуальном SysML-артефакте не означает готовности программных модулей.

#### 2.2.6 Зависимости {#226-dependency}

**Выбранное представление:** ориентированный граф «генератор использует каталог и валидатор; расчёт использует данные ингредиентов; покупки используют утвержденный план». Необязательные внешние API не должны становиться единственной точкой отказа при чтении уже сохранённого плана.

#### 2.2.7 Информация {#227-information}

**Выбранное представление:** логическая схема данных с версионированием состава рецепта и источника нутриентных значений. Неизвестные аллергены или неполные данные являются отдельным состоянием, а не пустым списком «без аллергенов». Адресует REQ-FUNC-002, REQ-FUNC-005, REQ-REL-001.

#### 2.2.8 Интерфейс {#228-interface}

**Выбранное представление:** HTTPS/JSON API с версиями контрактов и централизованными кодами ошибок. Операции профиля, плана, замены блюд и списка покупок описаны в DV-004. Адресует REQ-SEC-001–002 и раздел SRS 3.1.3.

#### 2.2.9 Взаимодействие {#229-interaction}

**Выбранное представление:** сценарии «создать меню», «заменить блюдо», «не найдены безопасные рецепты» с указанием границ транзакций. Адресует REQ-FUNC-004, REQ-FUNC-007, REQ-REL-001.

#### 2.2.10 Алгоритм {#2210-algorithm}

**Выбранное представление:** детерминированный конвейер фильтрации рецептов, построения кандидатов, оценки КБЖУ и составления списка. Безопасность ингредиентов проверяется до ранжирования и повторно перед сохранением. Адресует REQ-FUNC-002–009.

#### 2.2.11 Динамика состояний {#2211-state-dynamics}

**Выбранное представление:** автомат состояний заявки на генерацию `Draft → Validating → Generating → Ready` либо `Failed`, с сохранением прежнего плана при сбое. Адресует REQ-REL-001.

#### 2.2.12 Параллелизм {#2212-concurrency}

**Выбранное представление:** независимые пользовательские запросы обрабатываются параллельно; изменение одного плана сериализуется по версии записи. Конфликт обновления завершается явным отказом, чтобы не потерять замену блюда. Адресует REQ-FUNC-007, REQ-FUNC-010.

#### 2.2.13 Паттерны {#2213-patterns}

**Выбранное представление:** слоистая архитектура, разделение доменных вычислений и хранилища, стратегия «проверка ограничений независимо от ранжирования». Конкретный фреймворк не закреплён SRS.

#### 2.2.14 Развёртывание {#2214-deployment}

**Выбранное представление:** веб-клиент на статическом хостинге или за веб-сервером, API-приложение, реляционная БД, защищённые секреты и резервное копирование. CI/CD и окружения разработки/тестирования/продукции уточняются при утверждении ADR-005.

#### 2.2.15 Ресурсы {#2215-resources}

**Выбранное представление:** лимиты запросов, пул подключений БД, ресурсное ограничение времени генерации и мониторинг задержек. Исходная нагрузочная цель SRS: до 5 000 рецептов и 50 одновременных запросов, p95 чтения плана ≤ 2 с и генерации ≤ 10 с без пользовательской сетевой задержки.

## 4. Решения {#4-decisions}
Приведённые решения — **предлагаемые**, так как SRS определяет поведение и ограничения, но не закрепляет конкретный стек или архитектурный стиль.

### ADR-001 — Разделение веб-клиента и серверного API

- **ID:** ADR-001
- **Title:** Отдельные UI и серверная доменная логика
- **Context:** Требуются браузерная доступность, проверка прав и единая реализация расчетов.
- **Options:** 1) единое приложение с серверным рендерингом; 2) клиент + HTTP API; 3) полностью клиентское приложение.
- **Outcome:** Предлагается **клиент + HTTP API**, потому что проверки аллергенов, расчёты и доступ к персональным данным должны контролироваться сервером; технология UI остаётся открытой.
- **More Information:** DV-001, DV-002, DV-004; REQ-SEC-001–002.

## 5. Приложения {#5-appendixes}


1. **Не выбран технологический стек.** Язык серверной разработки, UI-фреймворк, СУБД и хостинг должны быть утверждены отдельно; в SRS они не зафиксированы.
2. **Не утверждён источник нутриентных данных.** Требуется проверить полноту, лицензии и процедуру обновления каталога.
