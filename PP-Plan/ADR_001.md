# ADR-001 — Разделение веб-клиента и серверного API

## Контекст и постановка задачи

Веб-приложение «ПП-План» позволяет пользователю задавать целевые значения КБЖУ, пищевые предпочтения и аллергии, формировать меню на семь дней, заменять блюда и получать список покупок. Обработка персональных настроек, проверка аллергенов и расчёт питательной ценности требуют согласованной логики, которая не должна зависеть от реализации интерфейса в браузере.

**Вопрос:** как разделить отображение и ввод данных от вычислений, проверок безопасности и хранения планов, сохранив возможность самостоятельного развития пользовательского интерфейса?

Связанные артефакты: SRS — разделы 3.1, 3.2, 3.3.2, требования `REQ-FUNC-001–010`, `REQ-SEC-001–002`; SDD — `DV-001`, `DV-002`, `DV-004`.

## Драйверы решения

1. **Безопасность:** проверка аллергенов, прав доступа и обязательных ограничений на стороне сервера.
2. **Единая бизнес-логика:** одинаковые правила расчёта КБЖУ, генерации меню и формирования списка покупок для всех пользователей.
3. **Сопровождаемость:** возможность отдельно изменять UI и серверные функции без дублирования доменных правил.
4. **Тестируемость:** автоматизированные проверки алгоритмов и интерфейсных контрактов независимо друг от друга.
5. **Сроки и бюджет MVP:** разумная сложность реализации и развёртывания.

## Рассмотренные варианты

1. Единое серверное приложение с генерацией HTML на сервере.
2. **Отдельный веб-клиент (Web UI) и серверное HTTP API.**
3. Полностью клиентское веб-приложение с вычислениями в браузере.

## Итог решения

**Выбранный вариант: отдельное серверное HTTP API + Web UI.**

Веб-клиент отвечает за ввод настроек, отображение недельного меню, рецептов, значений КБЖУ и списка покупок. Серверное API отвечает за валидацию данных, авторизацию, работу с каталогом рецептов и хранилищем, исключение запрещённых аллергенов, генерацию меню, расчёт КБЖУ и обновление списка покупок после замены блюда.

Связь Web UI и API осуществляется по HTTPS; предполагаемый формат обмена — JSON. Сервер остаётся источником достоверных результатов расчётов и проверок. Конкретные фреймворки и способ физического размещения компонентов этим решением не закрепляются: логическое разделение не обязательно означает разные серверы или домены.

### Последствия

- **Положительные:** единая реализация критических правил; возможность независимого тестирования и изменения компонентов; серверный контроль доступа к личным данным и сохранённым планам; потенциальное повторное использование API другими клиентами.
- **Отрицательные:** необходимость поддерживать и версионировать API-контракты; дополнительные сетевые запросы и обработка ошибок связи; необходимость настройки взаимодействия клиента и сервера.
- **Последующие обязательства:** документировать API и ошибки, реализовать серверную проверку авторизации, не доверять результатам клиентского расчёта и предусмотреть интеграционные тесты.

### Подтверждение

Решение считается соблюдённым, если:

1. Web UI обращается к серверу через определённые API-контракты и не обращается напрямую к базе данных.
2. Генерация недельного меню, проверка аллергенов и итоговый расчёт КБЖУ выполняются на сервере.
3. Сервер отклоняет запрещённый рецепт и не позволяет получать или изменять чужие планы независимо от поведения клиента.
4. Изменение блюда через API приводит к пересчёту КБЖУ и списка покупок; результат корректно отображается Web UI.
5. Контрактные и интеграционные тесты выполняются в процессе проверки MVP.

## Плюсы и минусы вариантов

### Единое серверное приложение с генерацией HTML

- **Хорошо:** меньше отдельных контрактов и проще первоначальное развёртывание.
- **Хорошо:** доменная логика может оставаться на сервере.
- **Плохо:** представление и серверные сценарии сильнее связаны, что затрудняет независимое развитие интерактивного клиента.

### Отдельный веб-клиент (Web UI) и серверное HTTP API

- **Хорошо:** отделены отображение и бизнес-правила, проверки выполняются в одном доверенном месте.
- **Хорошо:** серверные функции легко тестировать без браузера; API может обслуживать дополнительные интерфейсы.
- **Плохо:** необходимы поддержка API-контрактов, организация сетевых взаимодействий и обработка недоступности сервера.

### Полностью клиентское веб-приложение

- **Хорошо:** меньше серверной логики и возможна работа некоторых функций без подключения к сети.
- **Плохо:** нельзя доверять клиентским проверкам аллергенов, прав доступа и корректности расчётов в качестве единственного механизма контроля.
- **Плохо:** сложнее организовать централизованное хранение личных профилей и синхронизацию планов.
